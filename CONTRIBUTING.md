# Contributing

Thanks for looking. This repository holds the public half of AirPrompter
Team Agents: the wire protocol, the TypeScript and Python SDKs, the CLI and
daemon, and the conformance suite. Contributions are welcome — bug reports,
fixes, new provider wrappers, deployment manifests, docs. The guide below is
what a change needs to land.

## Ground rules

- **Be kind.** The [Code of Conduct](CODE_OF_CONDUCT.md) applies everywhere
  in this project.
- **Security issues go to security@airprompter.com**, never to a public
  issue. See [SECURITY.md](SECURITY.md).
- **Sign your commits off** (`git commit -s`). By adding `Signed-off-by` you
  certify the [Developer Certificate of Origin](https://developercertificate.org/):
  you wrote the change or have the right to submit it under this project's
  BSD-3-Clause licence. No CLA.
- **Never commit a key, a token, or prompt text from a real workspace.**
  Fixtures use the fakes in `sdk-typescript/packages/core/src/testing/` and
  `sdk-python/tests/control_plane.py`.

## Set up

```bash
git clone https://github.com/airprompter/airprompter-agent-sdk
cd airprompter-agent-sdk

# TypeScript (Node 20+)
cd sdk-typescript && npm ci && npm run typecheck && npm test && cd ..

# Python (3.10+): a venv with every distribution installed editable
cd sdk-python && python -m venv .venv && .venv/bin/python tools/install_dev.py && .venv/bin/python -m pytest -q && cd ..

# The protocol gate (schemas, examples, vectors, OpenAPI)
cd conformance && npm ci && npm test && npm run lint:openapi && cd ..

# The CLI
cd cli && npm ci && npm test && cd ..
```

CI runs the same commands on Ubuntu and Windows, Python 3.10 and 3.12, and
builds the CLI on three operating systems. A green local run is what CI
expects.

## What a change needs

| If you change… | Also do… |
|---|---|
| anything under `protocol/` | a matching change in `conformance/` (the reference verifier, or a new vector generated by the tool in `protocol/tools/`), a line in `protocol/CHANGELOG.md`, and — for a wire change — bump `protocol/VERSION`. Additive changes are a minor bump; a runtime on the previous minor must still verify the new documents. Vectors are byte-for-byte what the generators produce; CI checks that. |
| the TypeScript SDK | a test in `sdk-typescript/test/`, and the same behaviour in the Python SDK (the two are lockstep: one version, the same conformance vectors, the same store layout). If you cannot do the Python side, say so in the PR and we will. |
| the Python SDK | the mirror of the above. |
| a provider wrapper (`wrap`, the AI SDK middleware, LiteLLM) | a fake-client test (see `sdk-typescript/test/wrap.test.ts`, `sdk-python/tests/test_wrap.py`); the real-package tests are optional and skip when the package is not installed. |
| a public function's name or shape | a line in [`CHANGELOG.md`](CHANGELOG.md) under **Unreleased**, and the compat table (`cd sdk-typescript && npm run compat-table`). |
| customer docs (`docs/`) | `node docs/check-links.mjs` — every relative link and anchor must resolve. |

### Conventions

- One version across every package in a language (`sdk-typescript/scripts/version-lockstep.mjs`,
  `sdk-python/tools/version_lockstep.py`). Never bump one package alone.
- TypeScript: `exactOptionalPropertyTypes`, no default exports, no side
  effects at import in `agent-core`. Layer rules are linted (`npm run lint:imports`):
  core imports nothing of ours; sync, runtime and telemetry import core only;
  the facade imports all four.
- Python: no third-party dependency beyond `httpx` and `cryptography`; the
  provider packages stay optional extras.
- Nothing the SDK does may fail the customer's model call, and nothing it
  writes to disk or the network may carry prompt text, model output or an
  end-user identifier. A test that proves a change keeps both is welcome.
- Commit messages and PR titles say what changed in plain words, as a
  sentence; the body says why. See `git log` for the house style.

## Sending the change

1. Fork, branch from `main`, make the change with its tests.
2. Run the commands above for every part you touched.
3. Open a pull request against `main` using the template. A maintainer
   reviews within a few business days; small fixes usually land the same
   week.
4. Releases are cut by maintainers by tag (`sdk-typescript/vX.Y.Z`,
   `sdk-python/vX.Y.Z`, `protocol/vX.Y.Z`, `cli/vX.Y.Z`); the workflow
   publishes with provenance. You do not need to bump versions in a PR
   unless asked.
