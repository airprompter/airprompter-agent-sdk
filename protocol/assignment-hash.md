# Sticky assignment

An experiment (or a staged rollout, which is the same machinery — D19)
splits traffic between arms without any coordination between instances and
without the subject ever leaving the customer's process. Every SDK, the CLI
and the hosted run route must split identically, so the function is pinned
here and `vectors/assignment.json` is the test.

## Inputs

| Name | Source | Bytes hashed |
|---|---|---|
| `salt` | `manifest.payload.experiment.salt` — base64url without padding, random per experiment | the **decoded** bytes |
| `subject` | the value the customer passes (`{ subject: userId }`), falling back to the instance id when absent (then *instances* split, not users, and the console says so) | UTF-8 of the string, no normalisation, no trimming |
| `arms` | `manifest.payload.experiment.arms` in manifest order | — |

## Function

```
h      = SHA-256( decode_base64url(salt) ‖ utf8(subject) )
bucket = uint64_big_endian(h[0..8]) mod 10000
arm    = first arm i such that bucket < weightBps[0] + … + weightBps[i]
```

* `weightBps` are basis points and sum to exactly 10000, so the last arm is
  always reachable and every bucket maps to exactly one arm. An arm with
  weight 0 is never chosen.
* The order of `arms` in the manifest is part of the contract: a runtime
  must not sort them.
* The 64-bit unsigned interpretation is exact in every language; the
  modulus makes the result fit in a JavaScript number without BigInt, but
  the first eight bytes must be reduced as a full 64-bit integer — reducing
  32 bits would give a different bucket.

## What travels

* **Client mode:** nothing. The hash is computed locally and only the arm
  name appears on evidence and in telemetry.
* **Managed mode (§18):** the SDK sends `subjectHash = hex(h)` (lowercase,
  64 characters) to the run route, which reduces it to the bucket exactly
  as above. The raw subject is never sent.

Each experiment carries its own random salt, so an assignment never carries
over between experiments on the same tag, and a subject's bucket in one
experiment reveals nothing about another.

## The ramp plan (S9)

Weights used to ride the manifest one step per generation, so on an
`unlock_required` environment every step of a rollout waited for an
unlock, and every `stage()` wiped the other slot's payloads — the
rollback release — on every host. The plan now rides the manifest once:

```
experiment.ramp = [ { notBefore, weightBps[] }, … ]     (optional, 1–8 steps)
```

* `notBefore` is an instant on the **host's** clock, inclusive; steps are
  strictly increasing and at least **one hour** apart.
* each `weightBps` has one entry per arm, in manifest order, integers ≥ 0
  summing to exactly 10000.
* the weights in force at `now` are the **last** step whose `notBefore` ≤
  `now`; before the first step they are `arms[].weightBps`.
* a malformed plan refuses the manifest whole (`ramp_invalid`, trust-chain
  M14) — a runtime never walks a plan it cannot read.

The fleet walks the plan with no check-in: the customer on
`unlock_required` unlocks the plan once and the ramp proceeds on
schedule; bundle customers ramp offline. Sticky buckets make the walk
monotone — a subject that reached the candidate at one step is still on
it at the next — and two hosts with skewed clocks disagree only for
subjects in the range a step moved, and only for the skew.

The cloud can only **retreat**: `disable scope: "arm"` names an arm whose
share goes to the first arm in manifest order that is not disabled (the
control). It is a reduction, so it lands on an `unlock_required` host
without an unlock — from any manifest whose envelope verified, even one
left staged — and needs no new plan. Every arm disabled is a Freeze for
the tag. A `disable` naming an arm the manifest does not have changes
nothing. There is no `reweight` directive: an adjustment upward is a new
plan (a generation, which waits on `unlock_required` and applies on
`auto`); an in-envelope adjustment without an unlock would be an explicit
per-target waiver, never inherited, and is not built.

`vectors/ramp.json` (generated by `tools/gen_ramp_vectors.py`, an
independent implementation) is the test: the walk before / at / between /
after steps, two skewed hosts across a step, the retreat, an unknown arm,
and every refused plan.

## Vectors

`vectors/assignment.json` was generated by an independent Python
implementation (`hashlib`, `int.from_bytes(..., "big")`). Each case gives
the salt, the subject, the arm weights, and the expected `subjectHash`,
`bucket` and `arm`. The `refused` list names manifests an SDK must reject
before assigning: weights that do not sum to 10000, fewer than two arms, a
salt that is not base64url.
